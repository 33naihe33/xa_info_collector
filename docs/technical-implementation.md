# 雄安信息商机挖掘系统 — 技术实现文档

> 版本：1.0 | 日期：2026-07-13

本文档说明系统的技术实现方案，以及每个需求目标如何被技术实现满足。

---

## 一、需求目标回顾

本项目源自一个核心诉求：**从雄安新区官方网站抓取政务信息，用 AI 挖掘面向银行分行行长的金融业务合作机会，产出正式报告。**

细化为七个需求目标：

| 编号 | 需求目标 | 来源 |
|------|---------|------|
| R1 | 自动抓取雄安各类官方网站信息（领导会见、发文、招标、疏解等） | 用户原始设想 |
| R2 | 从信息中挖掘合作机会（银行金融业务视角） | 用户明确：面向银行分行行长（厅级） |
| R3 | 商机覆盖全行业务条线（对公/普惠/个金/政银，非仅对公） | 用户修正：不能只有对公 |
| R4 | Web 服务，桌面端三模式（商机/图谱/报告） | 用户选定方案 C |
| R5 | 产出正式报告，可导出 Word/PDF，按时间生成日/周/月报 | 用户明确 |
| R6 | 移动端随时随地查看 | 用户补充 |
| R7 | 信息主动推送，按时间或重要程度提醒 | 用户补充 |

## 二、系统架构

### 2.1 总体架构

系统分为六个独立模块，数据单向流动：

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  爬虫层   │ ─→ │  存储层   │ ─→ │  分析层   │ ─→ │ 报告/推送 │ ─→ │  服务层   │
│ Collector │    │ Storage  │    │ Analyzer │    │Reporter/ │    │   Web    │
│          │    │          │    │          │    │ Notifier │    │          │
│4数据源    │    │SQLite    │    │GLM-4-flash│   │Word/Push │    │FastAPI   │
│增量+限速  │    │10张表     │    │规则预筛   │    │          │    │Vue 3 PWA │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
```

### 2.2 技术栈

| 层 | 技术 | 选型理由 |
|----|------|---------|
| 爬虫 | httpx + BeautifulSoup | 官网是 SSR 静态 HTML，无需 Playwright；httpx 配合 respx 测试 |
| 存储 | SQLite + FTS5 | 本地部署零运维，单文件，足够支撑万级文档 |
| LLM | 智谱 GLM-4-flash | 中文公文理解好、成本极低（50篇分析约0.1元） |
| 后端 | FastAPI | 异步高性能，自动 API 文档，Python 生态无缝 |
| 前端 | Vue 3 + Element Plus + ECharts | 响应式 PWA 一套代码适配桌面/移动 |
| 报告 | python-docx | 正式公文排版，行长可直接转发批注 |
| 推送 | pywebpush + VAPID | PWA Web Push，无需安装 App |
| 调度 | APScheduler | Python 定时任务（每日抓取/定时摘要推送） |

## 三、各需求目标的技术实现

### R1：自动抓取雄安官方网站信息

#### 技术实现

**数据源发现**：通过实际探测雄安官网（xiongan.gov.cn），发现一个隐藏的 JSON datasource API——每个栏目页的 `<ul>` 标签上嵌有 `data="datasource:{32位hex}"` 属性，对应的 JSON 文件返回完整文章列表（最多1000条），无需翻页、无需 JS 渲染。

```
栏目页 /xaxw/zxyw.html
  → 发现 datasource:faa2cd6debde4c7bbacb8352bc94a894
  → JSON API: /xaxw/ds_faa2cd6debde4c7bbacb8352bc94a894.json
  → 返回1000条文章（标题/URL/时间/摘要/关键词）
```

**抓取流程**（BaseAdapter.run）：
1. 读取上次成功抓取日期（增量基准）
2. 调 JSON API 获取列表，按日期过滤新增条目
3. 逐篇抓取详情页，BeautifulSoup 解析正文
4. content_hash 去重，写入 documents 表
5. 保存原始 HTML 快照（防删稿/改版可回溯）

**并发控制**（用户特别强调）：
- 严格单线程顺序抓取，禁止任何并发
- QPS 限速：默认每0.5秒最多1个请求（`_throttle()` 强制间隔）
- 首次全量限制50条（INITIAL_BATCH），不全量扫1000条
- 增量爬取：基于 `crawl_runs.last_crawled_date`，只获取新增内容

**实体验证**：真实抓取50篇雄安官网新闻，正文抽取干净完整，平均每篇1200字，0错误。

#### 为什么满足 R1

| R1 要求 | 实现方式 |
|---------|---------|
| 抓取雄安各类官方网站 | 已接入中国雄安官网（4个栏目），架构支持扩展到公共资源交易、雄安集团采购、县区省级 |
| 领导会见 | 官网"最新要闻"栏目涵盖领导调研/会见报道 |
| 新发文 | "政策文件""通知公告"栏目 |
| 招标 | 公共资源交易平台（数据源配置已预留，adapter 待实现） |
| 自动化 | APScheduler 每日定时 + 手动触发 API |

### R2：挖掘银行金融业务合作机会

#### 技术实现

**两步 LLM pipeline**：

```
文档入库
  │
  ▼
规则预筛（rule_filter.py，零成本）
  关键词匹配：命中"项目/投资/疏解/招聘/签约"等信号词才调 LLM
  → 过滤掉天气预报、人事任免等无信号文档
  │
  ▼ （仅命中的文档）
实体抽取（LLM 调用 #1）
  GLM 从正文抽取机构/人物/项目实体 + 实体间关系
  → 写入 entities（744个）+ relations（511条）
  │
  ▼
商机研判（LLM 调用 #2，核心）
  GLM 按银行行长视角判断：
  - 是否构成金融商机？
  - 属于哪个业务条线？什么类型？
  - 预估金融规模？适配哪些产品？
  - 金融视角解读 + 建议行动
  → 写入 opportunities（32条）
```

**行长视角的字段设计**（opportunities 表）：
- `fin_scale`：预估金融规模——行长第一眼看量级
- `fin_products`：适配金融产品——直接对应业务条线分派
- `action_suggest`：建议行动——不只"发现"，还给"该怎么做"
- `priority`：critical/high/medium/low——按规模和重要性排序

**成本控制**：规则预筛跳过无信号文档，50篇文档实际只调94次LLM（非100次），总消耗124K tokens，成本约0.1元。

#### 为什么满足 R2

| R2 要求 | 实现方式 |
|---------|---------|
| 挖掘合作机会 | LLM 从政务新闻中识别金融业务信号（融资/存款/获客/合作） |
| 银行行长视角 | 提示词明确"服务银行分行行长"；商机字段含规模/产品/行动建议 |
| 智能分析 | GLM-4-flash 结构化 JSON 输出，非简单关键词匹配 |
| 可追溯 | 每条商机记录 source_doc_id，点开回到原文核实 |

### R3：商机覆盖全行业务条线

#### 技术实现

**四大业务条线 × 14种商机类型**，全部定义在 `config/opp_rules.yaml`（配置驱动，改配置不改代码）：

| 条线 | 商机类型示例 | 典型信号 |
|------|-------------|---------|
| 对公 corporate | 重大项目融资、央企入驻、机构存款、债券承销 | 开工/总投资/央企落户/专项资金 |
| 普惠 inclusive | 产业链配套、科创企业、商贸个体 | 产业链/创新园/商户 |
| 个金 retail | 代发工资、住房贷款、财富管理 | 招聘/商品房/高净值 |
| 政银 partnership | 战略合作、政策窗口 | 签约/数字人民币/绿色 |

**关键设计**：同一事件可触发多条线机会。例如央企迁入：
- 对公（开户结算融资）
- 普惠（产业链配套中小微）
- 个金（员工代发购房贷）
- 政银（战略合作信号）

**疏解落地特殊处理**：不是独立商机类型，而是按阶段（规划/建设/入驻）映射不同条线的金融需求——选址期做投行咨询，建设期做项目贷，入驻期做代发结算。

#### 为什么满足 R3

| R3 要求 | 实现方式 |
|---------|---------|
| 不能只有对公 | 四条线平等定义在 opp_rules.yaml，LLM 按完整条线表扫描 |
| 普惠/个金覆盖 | 14种类型涵盖普惠（科创/供应链/商贸）和个金（代发/房贷/财富） |
| 可扩展 | 增删条线/类型只改 YAML，不改代码 |

**实际验证**：32条商机分布为普惠29条、对公3条（近期官网新闻偏科创/人才主题，对公类项目信息更多在交易平台）。

#### 技术实现

**方案 C：双模式切换**（用户选定），顶部导航切换三个模式：

### R5：产出正式报告，可导出 Word

#### 技术实现

**报告生成流程**：
1. 用户选参数（日/周/月 + 时间范围 + 条线）
2. 后端查询该时段商机，构建摘要
3. GLM 汇总生成结构化报告（JSON：概要/分章节/建议）
4. python-docx 渲染为正式 Word 公文

**报告结构**（按业务条线分章节）：
```
雄安新区金融业务机会周报
（2026.07.04 - 2026.07.10）

一、本期概要（LLM 生成2-3句总结）
二、对公业务机会（逐条：规模/产品/解读/建议）
三、普惠金融机会
四、个人金融机会
五、政银合作机会
六、重点关注与建议（LLM 推荐最该跟进的商机）
```

**Word 排版**：python-docx 生成标题/正文/段落层级，正式公文格式，行长可直接转发批注。

#### 为什么满足 R5

| R5 要求 | 实现方式 |
|---------|---------|
| 正式报告 | python-docx 公文格式（封面标题/分章节/段落） |
| 按时间生成日/周/月报 | report_type 参数 + 时间范围选择 |
| 可导出 Word | GET /api/reports/{id}/export?format=docx → 下载 .docx |
| 按条线归口 | 报告按四条线分章节，各条线部门各取所需 |

### R7：信息主动推送，按时间或重要程度提醒

#### 技术实现

**双触发机制**（两类推送逻辑完全不同）：

| 触发方式 | 逻辑 | 内容 | 场景 |
|----------|------|------|------|
| 按时间（定时摘要） | APScheduler Cron 定时 | 汇总型 | 每日早报/每周摘要 |
| 按重要程度（即时预警） | pipeline 分析完成后立即评估 | 单条 | 重大项目/重大政策 |

**即时预警的四级检查**（push_manager.send_instant_alert）：
1. 优先级阈值：critical/high 触发，medium/low 攒入摘要
2. 去重：同一商机只推一次
3. 免打扰：夜间/周末可关（支持跨午夜时段如22:00-07:00）
4. 每日上限：默认≤5条，防轰炸

**优先级 → 推送策略**（config/push_rules.yaml）：
- critical（≥10亿/央企疏解）：即时推送，无上限
- high（≥1亿/政策窗口）：即时推送，每日≤5条
- medium/low：攒入定时摘要

**用户偏好**（PushSettings）：
- 预警阈值、关注条线、定时计划、免打扰时段
- 移动端"我的"页面可配置

**推送通道**：PWA Web Push（VAPID 协议），无需安装 App，浏览器/添加到桌面后收到系统级通知。

**pipeline 集成**：分析 pipeline 每产出一条商机，自动调用 send_instant_alert 评估推送（try/except 包裹，推送失败不影响分析）。

#### 为什么满足 R7

| R7 要求 | 实现方式 |
|---------|---------|
| 按时间推送 | APScheduler 定时摘要（每日早报/每周摘要） |
| 按重要程度推送 | pipeline 完成后即时评估，threshold 控制触发级别 |
| 不打扰 | 每日上限 + 免打扰时段 + 去重 |
| 可配置 | 移动端设置页调整阈值/条线/时段 |

## 四、关键设计决策说明

### 4.1 为什么用 SQLite 而非 MySQL/PostgreSQL

**需求**：本地/内网部署，单用户或小团队使用。

**决策**：SQLite 单文件数据库 + WAL 模式。
- 零运维：无需安装数据库服务，`data/xac.db` 一个文件
- 性能足够：万级文档、千级商机，FTS5 全文搜索毫秒响应
- 可迁移：数据全是标准 SQL，未来需要可平滑迁移到 PostgreSQL

### 4.2 为什么用 GLM-4-flash 而非 GPT-4

**需求**：分析中文政府公文，成本敏感。

**决策**：智谱 GLM-4-flash。
- 中文理解：对政务公文（"疏解""承接地""高质量发展"）理解准确
- 成本极低：50篇文档分析消耗124K tokens，费用约0.1元；每日增量5-10篇，日成本<0.05元
- 可切换：llm_client.py 封装了模型调用，改 config 里的 model 字段即可换模型

### 4.3 为什么规则预筛而不是全量调 LLM

**需求**：控制 API 成本。

**决策**：rule_filter.py 关键词预筛。
- 大部分政务新闻（会议通知、人事任免、天气）不含商机信号
- 预筛跳过这些，50篇实际只调94次（非100次）
- 配合增量爬取，每日只分析5-10篇新文档

### 4.4 为什么 PWA 而非原生 App

**需求**：移动端随时随地查看，快速交付。

**决策**：响应式 PWA（vite-plugin-pwa）。
- 一套代码：桌面/移动共享后端 API 和业务逻辑
- 可安装：添加到手机桌面，体验接近原生
- 无需上架：不用过 App Store / 应用商店审核
- 离线缓存：service worker 缓存已访问数据

### 4.5 为什么配置驱动（解耦设计）

**需求**：用户明确"试用后可能调整"。

**决策**：所有可变逻辑外置为 YAML/文本配置。
- `sources.yaml`：增删数据源
- `opp_rules.yaml`：调整商机分类/信号词/产品映射（最常改）
- `prompts/*.txt`：调 LLM 提示词效果
- `push_rules.yaml`：调推送策略

改配置不改代码，重启服务即生效。
